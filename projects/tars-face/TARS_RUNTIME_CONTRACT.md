# TARS Runtime Contract — Event Bus Specification

## Purpose

The event bus is the single communication backbone for all TARS subsystems.
Every component talks through the bus. No component calls another directly.

```
Sensor/Event
     |
     v
  Event Bus ------+--> TARS Face (browser UI)
                  |
                  +--> Dashboard (station screens)
                  |
                  +--> Memory/Persistence
                  |
                  +--> Cognitive Layer (optional)
```

Adding a new capability means: "subscribe to events." Not "rewrite TARS."

---

## 1. Event Format

Every event on the bus has this exact shape:

```typescript
interface TarsEvent {
    id: string;           // uuid v4
    source: string;       // which subsystem emitted it
    type: string;         // dot-notation event type
    timestamp: number;    // unix ms (Date.now())
    data: Record<string, unknown>;  // payload — never undefined
    domain?: string;      // "tars" | "system" | "home" | "infra" | "user"
    priority?: "low" | "normal" | "high" | "critical";
    ttl?: number;         // seconds before event expires (default 300)
}
```

### Rules

1. **`id` is always unique.** Generated by the publisher. Consumers use it for deduplication.
2. **`source` identifies the emitter.** Dot-notation: `"tars.face"`, `"tars.monitor.health"`, `"tars.monitor.docker"`.
3. **`type` is the event category.** Dot-notation: `"health.cpu"`, `"system.started"`, `"alert.smart_warning"`.
4. **`data` is always an object.** Never null, never a primitive. Empty object `{}` if no payload.
5. **`domain` is optional.** Filters events by logical group. Default `"tars"`.
6. **`timestamp` is set by the publisher.** Consumers should not trust ordering by timestamp alone — use sequence or wall-clock comparison.

## 3. Subscription API

### In-Process (Node.js services)

```typescript
interface EventBus {
    // Subscribe to all events matching a filter
    subscribe(filter: EventFilter, handler: EventHandler): Subscription;

    // Subscribe to exactly one event type
    on(type: string, handler: EventHandler): Subscription;

    // Subscribe once
    once(type: string, handler: EventHandler): Subscription;

    // Publish an event
    publish(event: TarsEvent): void;

    // Unsubscribe
    unsubscribe(sub: Subscription): void;

    // Get last N events (for late joiners)
    getHistory(count?: number, filter?: EventFilter): TarsEvent[];

    // Get current subscriber count
    getSubscriberCount(): number;
}

interface EventFilter {
    types?: string[];       // match any of these types (supports * wildcard)
    sources?: string[];     // match any of these sources
    domains?: string[];     // match any of these domains
    minPriority?: string;   // minimum priority level
}

interface EventHandler {
    (event: TarsEvent): void;
}

interface Subscription {
    id: string;
    unsubscribe(): void;
}
```

### Wildcard Patterns

| Pattern | Matches |
|---|---|
| `health.*` | All health events |
| `*.cpu` | Any CPU event from any source |
| `system.*` | All system lifecycle events |
| `tars.*` | All TARS autonomy events |
| `*` | All events |

### Browser (WebSocket)

The browser receives events as JSON messages over WebSocket. Same `TarsEvent` format.

> **⚠ NOTE — DESIGNED / FUTURE IMPLEMENTATION**: The subscription API below (`onEvent`, `sendEvent`, per-type filters) is part of the designed contract but **not yet implemented** in the current TARS_EVENTS client. The current browser client (`window.TARS_EVENTS` in `tars_face_v1.html`) exposes only `isConnected()`, `send()`, `connect()`, and `disconnect()`, and receives **all** events without filtering. Per-client event filtering is supported by `ws-bridge.js` (`_tarsFilter`) but not yet used by the browser.

```typescript
// Browser-side API (designed — not yet implemented):
interface TarsEventClient {
    // Subscribe to events from the server
    onEvent(type: string | string[], handler: (event: TarsEvent) => void): void;

    // Send an event to the server
    sendEvent(event: Partial<TarsEvent>): void;

    // Connection state
    isConnected(): boolean;

    // Reconnect settings
    reconnect(): void;
}
```

The browser can also subscribe to specific event types to receive only relevant messages:

```javascript
// Designed — not yet implemented in TARS_EVENTS client:
const client = TARS_EVENTS.connect("ws://tars-pi:8080/ws");

client.onEvent("health.*", (event) => {
    updateHealthDashboard(event.data);
});

client.onEvent("tars.*", (event) => {
    updateObservatory(event.data);
});
```

## 4. Publishing API

### From Node.js Services

```javascript
const { eventBus } = require("./event-bus");

eventBus.publish({
    source: "tars.monitor.health",
    type: "health.cpu",
    data: {
        percent: 34.2,
        tempC: 52.1
    },
    domain: "system",
    priority: "low"
});
```

### From Browser (TARS Face)

```javascript
// Sent via WebSocket
TARS_EVENTS.sendEvent({
    source: "tars.face",
    type: "tars.decision",
    data: {
        activity: "weather_observation",
        score: 0.87,
        reason: "curiosity high, wander fatigue low"
    }
});
```

## 5. Transport

| Consumer | Transport | Details |
|---|---|---|
| In-process services | Direct function call | Same Node.js process, zero latency |
| TARS Face (browser) | WebSocket | JSON over single persistent connection |
| Future: external tools | REST + Webhook | Optional HTTP endpoint for webhook forwarding |

### WebSocket Protocol

1. Client connects to `ws://<host>:<port>/ws`
2. Server sends `system.started` event on connect
3. Client sends events as JSON strings
4. Server broadcasts matching events to all clients
5. Client can send a subscription filter: `{ "subscribe": ["health.*", "tars.*"] }`
6. Server sends `system.heartbeat` every 30s
7. Client disconnects → subscriptions cleaned up

---

## 6. Event History

The event bus maintains a circular buffer of recent events (default 1000).

```javascript
// Late-joining subscriber gets recent history:
eventBus.getHistory(10, { types: ["health.*"] });
```

History is held in memory only. Phase 8.4 adds SQLite persistence for long-term storage.

---

## 7. Guarantees

| Property | Guarantee |
|---|---|
| Delivery | At-most-once per subscriber (no retry) |
| Ordering | Per-publisher ordering preserved (same `source` field) |
| Global ordering | Not guaranteed (use `timestamp` + `id` for causal chains) |
| Persistence | In-memory only (Phase 8.4 adds SQLite) |
| Blocking | Subscribers are called synchronously in the publish call. Services must not block in handlers. |
| Error isolation | One subscriber throwing does not affect other subscribers. Errors logged as `system.error` events. |
| Late joiners | `getHistory()` provides recent events for new subscribers |

## 9. Adding a New Capability

The pattern for any future integration:

```javascript
// 1. Subscribe to relevant events
eventBus.on("health.temperature", (event) => {
    if (event.data.tempC > 75) {
        // 2. Do something
    }
});

// 3. Optionally publish results
eventBus.publish({
    source: "tars.services.fan_control",
    type: "action.suggest",
    data: { action: "enable_fan", reason: "temperature threshold exceeded" }
});
```

No subsystem modification. No direct coupling. Subscribe and publish.

---

## 10. Contract Enforcement (Runtime)

The event bus validates every event on publish:

- `id` must be a non-empty string
- `source` must match `^[a-z][a-z0-9._-]+$`
- `type` must match `^[a-z][a-z0-9._-]+$`
- `timestamp` must be a positive integer
- `data` must be a non-null object
- Priority must be one of `low`, `normal`, `high`, `critical`

Invalid events are logged as `system.error` and dropped.
